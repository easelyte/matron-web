# Work-view fixtures — provenance

`work-view-{ok,ok-domain,ok-detail,empty,error}.json` are **real producer output**, not
hand-authored payloads. They are generated by running the actual producer CLI
over a small synthetic store:

```
# from the son-of-anton workspace root, PYTHONPATH unset
python3 -m scripts.contracts.generate_work_view_fixtures \
    --fixture-dir /opt/matron/web-journal/src/journal/__tests__/fixtures
```

The synthetic store lives in that generator (`FIXTURE_STORE`). Input is
controlled — small, stable, and free of live backlog text — while the
transformation under test (grouping, priority ordering, envelope shape, claim
serialisation, the `unassigned` bucket) is the real thing.

`work-view-ok-detail.json` is the same store run with `--include-detail`, i.e.
what a journal that advertises the optional `opened` / `next_action` / `owner`
loop fields returns. The other files are the producer's default output, which
omits those fields, so both wire shapes stay covered.

**Do not hand-edit these files.** A consumer-authored fixture can stay green
through a producer/consumer skew that would reject every real response, which is
the whole failure this guards against. Regenerate instead; the son-of-anton side
runs the same generator with `--check` and fails on drift.

## The one field that is not producer-final

`claim.liveness` is always `"unknown"` here. The producer CLI cannot reach the
journal's database handle, so it emits that placeholder and the journal's `/work`
route overwrites it per request from the `conversations` table.

Tests that need `live` / `stale` therefore construct those values explicitly
(see `work-view-pane.test.tsx`). That is deliberate and is the only field for
which a consumer-authored value is correct — every other field must come from
the generator above.
